# X Content Workflows

Use the branch that matches the user's task. Keep outputs compact; do not expose internal scoring unless useful.

## Create a post

1. Identify the content object: idea, source post, release, result, observation, benchmark, or argument.
2. Choose the format that best fits the object: Original, Quote, Thread, or Reply. Do not choose a format merely because it is more visible.
3. Load relevant private memory when enabled: `voice.md`, `patterns.md`, `results.md`, and `topics.md` as needed.
4. Establish the concrete thesis and verified facts. Remove claims that cannot be supported.
5. Draft 2-3 meaningfully different options. Vary at least one of thesis, evidence emphasis, framing, or structure.
6. Check each option for:
   - concrete first line;
   - specific nouns/verbs;
   - early payoff;
   - one central thesis;
   - short scan-friendly structure;
   - no generic hype/source paraphrase;
   - factual support;
   - useful ending.
7. Return the drafts first. Briefly distinguish them only when the choice is not obvious.

## Improve a draft

Diagnose before rewriting. Name the highest-value defects, not every stylistic possibility.

Use these dimensions:

- **Opener:** Does the first line name the actual object/result/problem, or start abstractly?
- **Specificity:** Are the model/tool/API/benchmark/failure mode and decision-relevant quantities named?
- **Nouns:** Are concrete developer objects carrying the sentence, or generic terms such as `AI`, `future`, `innovation`?
- **Verbs:** Do verbs describe what the system/user actually does?
- **Payoff:** Does the reader get the useful contrast/implication immediately?
- **Evidence:** Is the strongest supported fact doing real work?
- **Rhythm:** Are sentences/blocks easy to scan, with avoidable repetition removed?
- **Contrast:** Is there a real decision boundary rather than manufactured cleverness?
- **Ending:** Does it land on an implication/action/question rather than engagement bait?
- **Voice:** Does it sound like a technical builder rather than launch copy or generic influencer prose?

Then produce the strongest rewrite plus, when useful, one materially different alternative.

## Reply

1. Read the source and enough thread context to know what has already been said.
2. Find one missing useful contribution. Do not compete with the source for attention.
3. Prefer one compact paragraph.
4. Use a specific implementation detail, caveat, comparison, evaluation design, decision metric, correction, field observation, or genuine technical question.
5. Avoid generic praise, paraphrase, forced jokes, or a standalone post pasted into a reply box.
6. If the obvious contribution already exists in the thread and no distinct useful seam remains, recommend not replying.

## Learn from outcomes

1. Gather the post(s), source/context, format, timing if relevant, and actual observed results.
2. Separate the writing feature from distribution/context variables: source reach, relationship, topic momentum, media, account stage, timing, and conversation crowding.
3. State the observed result before the lesson.
4. Propose the narrowest candidate lesson that the evidence supports.
5. Include competing explanations and counterexamples.
6. Assign low/medium confidence. Use high only after repeated own-account evidence with few plausible alternatives.
7. If the user asked to persist learning and the private workspace is enabled, append the lesson to `candidates.md` using `references/evidence-and-memory.md`.
8. Do not promote it unless the user separately approves promotion.

## Format selection notes

- **Original:** use when the idea should become durable owned profile proof and stands without borrowed context.
- **Quote:** use when the source is useful context/evidence and the account has a distinct thesis.
- **Reply:** use when one compact contribution belongs inside the active conversation.
- **Thread:** use only when the reasoning genuinely needs sequence; do not inflate a single post into a thread.

## Variant quality

Bad variants change adjectives or sentence order while preserving the same idea.

Good variants may differ like:

- decision-metric framing vs architecture-boundary framing;
- quantified opener vs declarative system-boundary opener;
- concise observation vs evidence-first breakdown;
- direct implication vs falsifiable question.

Do not generate many variants merely to create choice.
